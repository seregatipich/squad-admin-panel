# ADR: `RemoteAdminListHosts.cfg` (servers pull) vs. the panel's push of `Admins.cfg`

- **Status:** Accepted
- **Date:** 2026-07-25
- **Issue:** `SYNC-9` (#39) — *[Исследование] RemoteAdminListHosts.cfg как альтернатива push'у*
- **Depends on:** `SYNC-3` (#36, managed-segment mechanics), `SYNC-5` (#38, per-server sync lifecycle)
- **Referenced by:** `docs/components/workers/config-sync/README.md` (evaluation outcome)

## Context

The panel today **pushes** the admin list. `worker-config-sync`
(`apps/workers/config-sync/`) synthesizes a marker-fenced *managed segment*
(`//SQUAD-PANEL BEGIN … //SQUAD-PANEL END`) from the role/player DB and writes it
into each server's `/var/lib/squad-panel/configs/<id>/ServerConfig/Admins.cfg`
atomically through the host bridge. This is the mechanism the `2026-05-01`
architecture decision established (`docs/architecture/decisions.md`) and that
SYNC-3/SYNC-5 shipped. Concretely, per push cycle
(`apps/workers/config-sync/src/syncer.ts`):

- The segment body is generated by the shared, Node-free formatter
  `buildManagedSegmentBody` (`packages/shared-config/src/admins-config.ts`) —
  `Group=<role>:<perms>` lines followed by `Admin=<eosId>:<role> // <comment>`
  lines, deterministically ordered so a **sha256 over the body is stable**
  (`segment.ts:hashSegment`).
- The worker reads the current file, hashes the located segment, and writes
  **only if the hash differs** (`syncer.ts:173-226`) — idempotent, and content
  outside the markers (sqstat's `//SQSTAT DELIMETER`, manual edits) is preserved
  verbatim (`spliceManagedSegment`).
- After every successful write the worker issues an RCON `AdminReloadServerConfig`
  (best-effort, via worker-rcon — `src/rcon-reload.ts`) so the change **takes
  effect immediately**; Squad does not reliably re-read `Admins.cfg` on its own
  (SYNC-3 correction №1, `docs/components/workers/config-sync/README.md`,
  `changelog.md` 2026-07-25). Push therefore actively *forces* application — the
  panel is not at the mercy of any server-side polling timer.
- Every write emits a per-server audit row (`admins_cfg.synced` /
  `admins_cfg.force_synced`) and every bridge error emits `admins_cfg.sync_failed`
  (`syncer.ts:263-288`, `142-156`, `237-251`).
- A state machine is published to `admins-cfg:status:<id>` in Redis
  (`unknown | in_sync | drift | unreachable | syncing`) with `unreachable_since`
  tracking, driving the `/servers/<id>` UI banner (`syncer.ts:17-79`). SYNC-5
  raises a ">1 h unreachable" alert off `unreachable_since`.
- A 5-minute **drift sweep** re-reads each file, and on a managed-segment
  mismatch publishes `state='drift'` *without* auto-overwriting — the operator
  is offered a Force-sync button (`index.ts:303-324`, `syncer.ts:180-206`).
- Delivery is at-least-once and self-healing: a durable Postgres outbox
  (`relayAdminsCfgSyncOutbox`), Redis-Streams consumer group `config-sync`, and
  an `XAUTOCLAIM` reclaim sweep replay any event whose write did not land
  (`index.ts:116-289`).

Squad also supports a **pull** mechanism. `RemoteAdminListHosts.cfg` (one of the
19 `ALLOWED_CONFIG_FILES`, and one of the four `HOT_RELOAD_FILES` Squad re-reads
live — `packages/shared-config/src/bridge-methods.ts:62-94`) holds a list of
HTTP(S) **URLs**; the dedicated server fetches each URL on an interval and merges
the returned admin lists into its in-memory admin table. The file format the URL
must return is the **same** `Group=`/`Admin=` grammar as `Admins.cfg`, and
entries from multiple lists are unioned
(`ai_docs/plans/2026-07-04-task-decomposition.md:27`).

The question SYNC-9 poses: could the panel **host** the admin list at one internal
URL and let every server pull it — replacing (or complementing) the per-file
push — to simplify multi-server sync? That trade turns on three measured
behaviours (reload cadence, unreachable-URL handling, multi-list merge) and on
what the push architecture provides that a pull cannot. The panel already ships a
working "host a list at a URL" surface — the CBAN-5 outbound ban federation route
`GET /api/v1/public/banlist` (`apps/api/src/routes/public-banlist.ts`,
`apps/api/src/lib/banlist-publish.ts`,
`packages/db/src/schema/banlist-publication-settings.ts`) — so Option B below can
be costed against real, shipped code rather than a hypothetical.

## Options

### Option A — Stay on push (status quo)

Keep `worker-config-sync` as the single writer of the `Admins.cfg` managed
segment, exactly as SYNC-3/SYNC-5 ship it (described in Context). The panel is
authoritative; every role/player mutation enqueues a sync event; the worker
reconciles the file, records per-server audit + status, and surfaces drift and
outages. No new externally reachable surface; the admin list never leaves the
host bridge boundary.

### Option B — Panel hosts, servers pull

The panel exposes the managed segment at an internal, token-gated URL; each
server's `RemoteAdminListHosts.cfg` points at it and Squad pulls on its own
interval. This is **not hypothetical** — it is the CBAN-5 pattern re-pointed at
the admin domain:

- **Route** — a read-only `GET /api/v1/public/admin-list` modelled line-for-line
  on `public-banlist.ts`: token-gated on a `PermissionKey` scope
  (`banlist:read` → an `admins:read` analogue), rate-limited, `config: { audit:
  false }`, and gated on an `enabled` master switch read from a singleton settings
  row (the `banlist_publication_settings` shape,
  `packages/db/src/schema/banlist-publication-settings.ts`).
- **Body** — reuse `buildManagedSegmentBody`
  (`packages/shared-config/src/admins-config.ts`) unchanged, so the bytes the URL
  serves are **identical** to what push writes today. The `Group=`/`Admin=`
  grammar Squad expects from a remote host is exactly what that formatter already
  emits.
- **Caching** — reuse the `public-banlist` ETag/`If-None-Match` → `304` +
  `Last-Modified` handling verbatim (`public-banlist.ts:72-181`), so a server that
  polls a stable list transfers no body. This is the piece that is **grounded
  locally** (see Measurements Q1).
- **Wiring** — the config-sync worker would, per server, write the single
  `RemoteAdminListHosts.cfg` line (still a bridge `file_atomic_write`, still a
  managed segment) instead of the full `Admins.cfg` segment. So push does not
  disappear; it shrinks to publishing *one URL* per server, and the admin *content*
  moves to the pull path.

### Option C — Hybrid: push is source of truth, URL published alongside

Keep Option A's push as the authoritative, audited, drift-detected path, **and**
additionally expose the Option B read-only URL for consumers that genuinely need
pull semantics (an off-host server the bridge cannot reach; a federated/second
panel; an operator's own tooling). `Admins.cfg` on panel-managed hosts stays
push-written and authoritative; the URL is a published *view*, never the only
delivery path — so none of Option A's guarantees are lost, and the pull surface
exists where it adds value.

## Measurements

A live Squad dedicated server cannot be hosted in this environment (≈12 GiB
depot, `--network host`, UDP game/query ports — `ai_docs/plans/2026-07-04-task-decomposition.md`
SRV-1/SRV-2). Following the repo's established env-gating precedent for
Squad-behaviour research (`ai_docs/research/vote-log-format.md:13-18`,
`ai_docs/research/combat-log-format.md:12-16`), each of the three questions below
records either a **measurement grounded in-repo** (with the procedure/artifact
that produced it) or an **env-gated** row carrying (a) a reproducible measurement
protocol and (b) a live-validation checklist item. The production host
`tk104.duckdns.org` is deliberately **not** used for any experiment (a pull
mis-measurement there is production-impacting and irreversible).

| # | Question | Result | Grounding / status |
|---|---|---|---|
| Q1 | Remote-list **reload cadence** | Local `Admins.cfg` push path is re-read by Squad **~every 60 s** (in-repo operational note). Remote-URL fetch interval: **env-gated** — measured via HTTP access-log inter-arrival on a controlled host. | Q1 below |
| Q2 | Behaviour when the **panel URL is unreachable** | Squad retains the **last successfully-fetched** list in memory and logs a fetch error (design intent); the **cold-start-with-dead-URL** outcome (zero admins vs. skip) is the dangerous unknown. **env-gated.** | Q2 below |
| Q3 | **Multi-list merge** semantics | Entries from multiple remote lists (and the local `Admins.cfg`) are **unioned** by `Group`/`Admin`; per-list precedence on a duplicate `Group=` name is the unknown. **env-gated.** | Q3 below |

### Q1 — Reload cadence

**Grounded (push side).** Push propagation is now **effectively immediate and
panel-forced**: after each successful atomic write the worker issues an RCON
`AdminReloadServerConfig` (`apps/workers/config-sync/src/rcon-reload.ts`; SYNC-3
correction №1, `docs/components/workers/config-sync/changelog.md` 2026-07-25), so
a role/admin change applies on the next reload round-trip rather than waiting on
any timer. Absent that active reload, the documented passive fallback is that
Squad re-reads the on-disk `Admins.cfg` only **~every 60 s**
(`docs/components/workers/config-sync/troubleshooting.md`). Either way push has a
bounded, panel-controlled propagation — and crucially the panel can *force*
application, which the pull path structurally cannot (a server pulls on its own
timer; the panel has no way to make it re-fetch on demand — see Q1 checklist (c)).

**Grounded (hosting prototype).** The panel can serve a pulled list cheaply
today: the CBAN-5 route computes a sha256 ETag, sets `Last-Modified`, and returns
**`304 Not Modified`** on a matching `If-None-Match`
(`apps/api/src/routes/public-banlist.ts:72-181`). This is proven by an existing
integration test — `apps/api/test/integration/banlist-publish.test.ts:407-423`
("ETag: a repeated GET with If-None-Match returns 304") asserts `statusCode ===
304`. So even a *frequent* server poll of an Option-B admin-list URL costs one
conditional GET with an empty body while the list is unchanged; bandwidth is not
a reason to prefer push or pull.

**Env-gated (pull-side cadence).** Squad's actual remote-fetch interval is not
published in any source reachable from this environment (the Squad Fandom wiki is
not fetchable here — same limitation recorded in
`ai_docs/research/vote-log-format.md`). *Measurement protocol:* stand up a
controlled HTTP server (the Option-B route, or a static file server with request
logging), point one live Squad server's `RemoteAdminListHosts.cfg` at it, and
measure the **inter-arrival time of `GET` requests in the access log** across ≥3
fetches; that interval is the reload cadence, measured without reading Squad's
closed source. *Live-validation checklist:* (a) confirm the steady-state fetch
interval; (b) confirm whether a fetch fires at server **boot** in addition to the
periodic timer; (c) confirm whether editing `RemoteAdminListHosts.cfg` (a
`HOT_RELOAD_FILE`) forces an immediate re-fetch or only takes effect on the next
timer tick.

### Q2 — Unreachable-URL behaviour

**Grounded (push side).** The push path treats bridge unreachability as a
**first-class, observable** state: a failed `file_read`/`file_atomic_write`
publishes `state='unreachable'` with `unreachable_since`, writes an
`admins_cfg.sync_failed` audit row, and leaves the Redis-stream message unacked
for `XAUTOCLAIM` retry until it succeeds (`syncer.ts:131-166`, `227-261`;
`index.ts:188-206`). SYNC-5 escalates a >1 h outage to an operator alert. Failure
is loud, per-server, audited, and self-healing.

**Env-gated (pull side).** The failure mode of the pull path is the crux of the
verdict, and it is **silent** by construction: if the server has fetched the list
at least once and the URL later goes unreachable, Squad keeps serving the
**stale** in-memory list with no signal the panel can see — the panel has no
per-server delivery receipt, no `unreachable_since`, no audit row, because
nothing on the panel side even knows a given server failed to poll. The
genuinely unknown and higher-risk sub-case is a **cold start against a dead URL**
(panel down during a server (re)start): does Squad start with **zero** admins, or
skip the unreachable host and continue? *Measurement protocol:* (1) point a live
server at the controlled URL, let it fetch once, confirm admins via RCON
`AdminListAdmins`; (2) take the URL offline (stop the server / return `500` /
drop the connection) and re-check `AdminListAdmins` to see whether the list
persists; (3) **restart** the Squad server while the URL is still offline and
check `AdminListAdmins` on cold start. *Live-validation checklist:* (a) confirm
last-fetched list persists across an outage; (b) confirm the cold-start-dead-URL
outcome (admins present vs. empty); (c) capture the exact log line Squad emits on
a failed fetch (needed before pull could ever be monitored); (d) confirm timeout
vs. connection-refused vs. HTTP-error are handled identically.

### Q3 — Multi-list merge

**Grounded (design fact).** The panel's own decomposition records that Squad
**unions** permissions across multiple remote lists and the same-format file
applies (`ai_docs/plans/2026-07-04-task-decomposition.md:27`). The Option-B body
is byte-identical to the push segment (`buildManagedSegmentBody`), so a merged
setup — panel URL **plus** a hand-maintained local `Admins.cfg` or a second
community list — is expressible without a new formatter.

**Env-gated (merge precedence).** What is unverified is the **precedence** when
two sources define the *same* `Group=` name with different permission sets, or
the same `Admin=` EOS id with different groups: union of permissions, last-list-
wins, or first-list-wins. This matters because the panel's drift model assumes it
is the *single* writer of a self-contained segment; under merge, a second list
could silently grant permissions the panel neither wrote nor audits.
*Measurement protocol:* host two lists — List A `Group=Mod:kick`,
`Admin=<eos1>:Mod`; List B `Group=Mod:ban`, `Admin=<eos1>:Mod` plus
`Admin=<eos2>:Mod` — reference both in `RemoteAdminListHosts.cfg`, and read the
effective permissions of `<eos1>` via RCON to determine whether `Mod` resolves to
`kick`, `ban`, or `kick,ban`. *Live-validation checklist:* (a) determine
duplicate-`Group=` resolution (union vs. override); (b) confirm local
`Admins.cfg` and remote lists co-exist and merge rather than one disabling the
other; (c) confirm list ordering in `RemoteAdminListHosts.cfg` is or is not
significant.

## Decision

**We stay on push (Option A); the pull URL is recorded as an opt-in Follow-up
(Option C), not a migration.**

On the evidence assembled above, migrating the admin list from push to pull would
**trade a set of shipped, load-bearing guarantees for operational simplicity that
push already delivers**, while introducing a silent-staleness failure mode:

- **Loss of drift detection.** Push owns a self-contained sha256-hashed segment
  and detects out-of-band edits within one 5-minute sweep (`index.ts:303-324`).
  Under merge (Q3), a second list can inject admins the panel never wrote and
  cannot see — the single-writer invariant that makes drift detection meaningful
  is gone.
- **Loss of per-server audit and status.** Push writes `admins_cfg.synced` /
  `.force_synced` / `.sync_failed` per server and maintains the
  `admins-cfg:status:<id>` state machine. Pull has **no per-server delivery
  receipt** — the panel cannot know which server actually pulled which version, so
  the audit trail and the `/servers/<id>` banner both go dark.
- **New silent-staleness failure mode (Q2).** When the panel URL is unreachable,
  push surfaces `unreachable` + `unreachable_since` and the SYNC-5 >1 h alert;
  pull keeps serving a stale in-memory list invisibly, and the cold-start-dead-URL
  outcome is an unquantified risk that could leave a server with **zero** admins.
- **No cadence advantage, and loss of forced application (Q1).** Push now *forces*
  an immediate RCON `AdminReloadServerConfig` after each write, and the ETag/304
  hosting prototype makes even frequent polling cheap — so pull buys no propagation
  win. Worse, pull *removes* the panel's ability to force application at all: a
  server picks up a change only on its own fetch timer, which is unacceptable for
  time-sensitive admin grants and in-game kicks/bans.

**Reversal conditions** — revisit this decision (toward Option B, a real
migration) if *all three* hold:

1. Q2 live validation shows Squad **fails safe** on an unreachable URL (retains
   the last list on outage **and** never cold-starts to an empty admin table),
   AND emits a fetch-failure log line the panel can ingest to reconstruct
   per-server delivery status.
2. Q1 live validation shows either a remote-fetch cadence fast enough for
   time-sensitive admin grants/kicks, or a supported way for the panel to *force*
   an on-demand re-fetch — recovering the forced-application property push now has
   via RCON `AdminReloadServerConfig`. A pull path that only applies on the
   server's own slow timer is disqualifying.
3. The panel's operational scale grows to servers the host bridge **cannot**
   reach for `file_atomic_write` (off-host / third-party-hosted), where push is
   not merely more work but structurally impossible — at which point pull stops
   being an alternative to push and becomes the *only* option for those hosts.

## Consequences

**Positive**

- Zero code, schema, migration, or dependency change. The shipped SYNC-3/SYNC-5
  push path — drift detection, per-server audit, the outage state machine, the
  >1 h alert, at-least-once delivery — is preserved intact and remains the single
  source of truth for who is an admin where.
- The admin list never leaves the host-bridge trust boundary; no new externally
  reachable, token-gated surface is added to the panel's attack surface for a
  capability push already covers.
- A concrete, costed migration design (Option B) and the exact live experiments
  that would justify it (the three protocols above) are on record, so a future
  revisit starts from measurements, not from scratch.

**Negative / accepted trade-offs**

- Multi-server sync stays a **push** problem: every server needs bridge
  reachability and its own reconcile/retry, rather than each server self-serving
  from one URL. For the current on-host, bridge-reachable fleet this is already
  solved by SYNC-5; it becomes a real limitation only if off-host servers appear
  (reversal condition 3).
- Servers the bridge cannot reach cannot be admin-synced at all under push — the
  hybrid URL (Follow-up) is the intended escape hatch for that case, not a
  general migration.
- The three pull behaviours (Q1–Q3) remain **env-gated / unverified** until a
  live Squad host runs the protocols; this ADR's verdict rests on the push side's
  known guarantees and on the *asymmetry of failure modes*, not on disproven pull
  behaviour. The reversal conditions are written precisely so that running those
  experiments can overturn the decision if the evidence warrants.

## Follow-up not covered by this issue

1. **Hybrid publish URL (Option C).** A read-only `GET /api/v1/public/admin-list`
   that serves `buildManagedSegmentBody` output with the CBAN-5 ETag/304 +
   token-gate + `enabled` singleton, as a *view* alongside authoritative push —
   for off-host servers, a federated second panel, or operator tooling. Scoped as
   its own feature issue; push remains source of truth.
2. **Run the three live experiments** (Q1 cadence, Q2 unreachable/cold-start,
   Q3 merge precedence) against a real Squad host when one is available, and
   record the results as an `ai_docs/research/remote-admin-list-hosts.md` pin
   (same shape as the vote-/combat-log pins). If they satisfy the reversal
   conditions, open a migration ADR that supersedes this one.
3. **Pull monitoring prerequisite.** If pull is ever adopted, per-server delivery
   status must be reconstructed from the panel URL's own access log (which server
   pulled which ETag, and when) to recover the observability push provides
   natively — designed as part of any future migration, not retrofitted after.

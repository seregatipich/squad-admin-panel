# Подтверждаемая доставка VIP в `Admins.cfg`: проект решения

## Результат

Панель принимает желаемое VIP-состояние от `site-backend`, безопасно назначает
роль, доставляет managed-сегмент `Admins.cfg` на каждый активный сервер и даёт
сайту подписанное состояние конкретного события. Ответ `202` означает только
принятие. Итог `applied` появляется после устойчивой фиксации результата
доставки по каждому серверу.

## Подпись и защита от повтора

Preflight, lifecycle и status используют одни заголовки `x-vip-timestamp` и
`x-vip-signature`. Timestamp сохраняет действующий совместимый формат ISO 8601
с часовым поясом; панель принимает его только в окне ±300 секунд от серверного
времени и затем проверяет
`HMAC-SHA256(timestamp + "." + canonicalJson(body))` через
`timingSafeEqual`. Значение вне окна, дата без часового пояса, неверный формат
и неверная подпись дают
одинаковый `401 { "error": "invalid_signature" }`.

Окно ограничивает повтор перехваченного запроса, а бизнес-идемпотентность
задают `event_id`, `revision` и хеш запроса. Для каждого принятого lifecycle
панель сохраняет SHA-256 канонического проверенного тела без заголовков:

- повтор того же `event_id` и того же `request_hash` возвращает
  `200 { "ok": true, "duplicate": true }` без новой мутации, аудита и outbox;
- тот же `event_id` с другим телом возвращает
  `409 { "error": "event_body_conflict", "error_code": "event_body_conflict" }`
  без эха идентификаторов;
- одна revision может принадлежать только одному событию игрока: частичный
  unique index `(player_id, revision) WHERE revision IS NOT NULL` страхует от
  гонок и обходных путей. Другой `event_id` с уже занятой revision возвращает
  `409 { "error": "revision_conflict", "error_code": "revision_conflict" }`.

## Входной договор и preflight

До покупки сайт вызывает preflight по SteamID64, tier и role id. Панель
подтверждает только текущий снимок:

- игрок существует и его непустой EOS включён в проекцию игрока;
- роль соответствует указанному активному `vip_tiers`, не системная и не даёт
  `panel_access`;
- у игрока нет активной `vip_subscriptions`, которой владеет внутренний
  биллинг панели;
- роль игрока пуста либо текущее назначение доказуемо принадлежит тому же
  внешнему lifecycle. Та же VIP-роль, назначенная вручную, — это
  `manual_role_conflict`, а не разрешение на перезапись;
- существует хотя бы один неудалённый сервер.

Успешный ответ содержит `{ ok: true, servers_total, projection_owner,
expires_at }`. `projection_owner` равен `bss-store` только для доказанного
внешнего назначения; `expires_at` берётся из текущей проекции и нужен сайту для
безопасного максимума сроков. Значение `servers_total` информативно: lifecycle
обязан повторить все проверки и заново получить непустой список серверов в
своей транзакции.

Lifecycle-событие содержит стабильные `event_id`, `purchase_id`, положительную
монотонную `revision`, тип события и желаемый абсолютный срок. Для переходной
совместимости `discord_id` допускается схемой, но игнорируется: панель не
владеет Discord-ролью. Пока выключен флаг
`VIP_LIFECYCLE_REQUIRE_REVISION`, допускается старое тело без revision; после
обновления producer флаг делает revision обязательной. Даже при выключенном
флаге legacy-событие разрешено только пока у игрока ещё нет ни одного события
с revision: старый producer не может переиграть уже начатую revision-цепочку.
Каждая оплаченная покупка сайта получает новый `purchase_id`; поэтому
`vip.extended` с большей revision вправе передать проекцию от предыдущей
покупки следующей внутри владельца `bss-store`. Точное совпадение
`purchase_id` обязательно для снятия, но не для такого оплаченного продления.

Постоянная ошибка возвращает канонический безопасный `error_code` и переходный
совместимый псевдоним `error` с тем же значением. Старый отправитель продолжает
читать `error`, новый использует `error_code`; после миграционного окна
псевдоним можно удалить отдельным изменением договора.

## Сериализация и владение ролью

Lifecycle выполняется в одной транзакции. Сначала он выбирает игрока через
`SELECT ... FOR UPDATE` с явной проекцией `id`, `steam_id64`, `eos_id`,
`role_id`, `role_expires_at`, `role_comment` и `role_lifecycle_event_id`. Эта же
блокировка сериализует
его с ручной покупкой/подпиской, которая уже использует либо должна использовать
блокировку строки игрока.

Под блокировкой сначала разрешается точный duplicate, затем проверяется
семантическая валидность нового тела и только после неё — порядок revision.
Меньшая revision может быть записана как `superseded` без проверки текущего
владения ролью и снимка серверов, потому что она ничего не меняет; это
гарантирует одинаковый итог для перестановок событий. Для новой победившей
revision затем повторяются проверки EOS, активного tier, безопасной роли,
текущего назначения и активной `vip_subscriptions`. Внешний lifecycle не
изменяет и не отменяет внутреннюю подписку. Ручное изменение роли выигрывает:
последующее внешнее продление или снятие не перезаписывает его. Владение
внешним назначением доказывается точным указателем текущей проекции на
действующее lifecycle-событие того же игрока. Совпадения одного `role_id`
недостаточно. Новая оплаченная purchase-revision может сменить этот указатель;
снятие обязано совпасть с `purchase_id` текущего указателя.
Для компенсирующего deactivation-события `vip.refunded` или `vip.expired`
будущий абсолютный `expires_at` означает восстановление внешней проекции до
этого срока и перенос указателя на новое событие. Только отсутствующий либо
истёкший `expires_at` означает снятие, для которого сохраняется точное
совпадение `purchase_id` текущего указателя.

Миграция не угадывает владельца старой роли: существующее назначение с пустым
`role_lifecycle_event_id` безопасно считается ручным. Перед включением нового
producer выпуск обязан обезличенно посчитать такие назначения, совпадающие с
историческими `assigned`-событиями. Нулевой результат допускает продолжение;
ненулевой останавливает включение до отдельного проверенного восстановления
указателей — автоматический backfill по одному совпавшему сроку запрещён, потому
что он не отличает последующий ручной перехват той же роли.

Ревизия монотонна для игрока целиком, а не для отдельной роли:

- новая большая revision назначает/продлевает безопасную VIP-роль либо снимает
  только своё ещё действующее внешнее назначение;
- новая revision после всех проверок вставляется первой, затем в той же
  транзакции помечает прежние незавершённые события игрока
  `superseded_by_event_id`; их status сразу становится `superseded`;
- пришедшая после победителя меньшая revision записывается как
  `action=superseded`, ссылается на победившее событие и не меняет игрока,
  аудит назначения или outbox;
- совпавшая revision другого события — явный `revision_conflict`, а не
  «безопасный повтор»;
- снятие с устаревшей revision, другой покупкой, иной текущей ролью или после
  ручного изменения не снимает новое/чужое назначение.

После проверок lifecycle заново выбирает неудалённые серверы. Пустой снимок
даёт `409 { "error": "no_target_servers", "error_code": "no_target_servers" }`
и откатывает событие, роль, аудит и
outbox. Для непустого снимка та же транзакция изменяет роль, пишет lifecycle и
создаёт ровно одну outbox-строку на каждый id из снимка с
`correlation_id=event_id`. Commit либо сохраняет всё перечисленное, либо ничего.

## Outbox после commit

API никогда не публикует Redis-сообщение из транзакции и не содержит
«быстрого» пути публикации. `publishAdminsCfgSyncForAllServers` только пишет
PostgreSQL outbox. Отдельный relay видит строку лишь после commit, публикует
payload с `_outbox_id` и сохраняет `relayed_at`/`stream_id`. Если процесс упал
после `XADD`, но до отметки в PostgreSQL, повторная публикация допустима и
обрабатывается идемпотентно.

Outbox дополнительно хранит `correlation_id`, `applied_at`, безопасный
`last_error` и итог `reload_outcome`. Сырые ответы RCON, SteamID64, EOS, путь и
содержимое конфигурации в нём не сохраняются.

## Доставка и подтверждение

Worker получает `_outbox_id`, строит managed-сегмент из свежего снимка БД,
проверяет/пишет файл и не подтверждает stream раньше устойчивого результата в
PostgreSQL. Совпавший хеш означает, что файл уже доставлен, но не заменяет
необходимое подтверждение живой перезагрузки для ещё не применённой outbox.

После файловой операции worker повторно читает `servers.status`; перед записью
`applied_at` читает его ещё раз, чтобы не принимать решение по устаревшему
состоянию:

- если сервер в `running`/`starting`, worker отправляет
  `AdminReloadServerConfig` с детерминированным request id от `_outbox_id`, ждёт
  валидный `rconCommandResult` с совпадающими server/request/command и `ok=true`,
  затем атомарно сохраняет `reload_outcome=confirmed` и `applied_at`;
- если при финальной проверке сервер уже не живой, успешной записи файла
  достаточно: сохраняется `reload_outcome=file_ready_for_restart`, потому что
  файл будет прочитан при следующем запуске;
- если сервер стал живым между проверками, worker обязан выполнить RCON-ветку,
  а не отметить строку применённой по прежнему stopped-снимку;
- unavailable, timeout, rejected, несовпавший/повреждённый результат либо
  ошибка bridge/Redis оставляют `applied_at=NULL`, записывают только безопасный
  код и оставляют сообщение без `XACK` для reclaim.

Устойчивым подтверждением является запись результата в PostgreSQL outbox, а не
сам эфемерный Redis result key. `XACK` выполняется только после этой записи.
Если worker упал после команды или файловой записи, повтор использует тот же
request id, сверяет outbox и состояние сервера и безопасно заканчивает работу.
Если он упал после `applied_at`, но до `XACK`, повтор только подтверждает
сообщение. Повторная RCON-команда также безопасна: reload идемпотентен.

## Запрос состояния

Подписанный status-запрос по `event_id` читает lifecycle и связанные outbox
строки. Ответ не содержит SteamID64, EOS, путь файла или конфиг:

- `accepted`, `applying`, `applied`, `failed` либо `superseded`;
- действие роли и `superseded_by_event_id` только для служебной корреляции;
- `servers_total`, `servers_applied`, `servers_pending`;
- безопасные коды проблем по серверу без секретов.

`applied` возможен только когда каждая коррелированная outbox-строка имеет
`applied_at`. `superseded` имеет приоритет над состоянием старых outbox: их
повтор всё равно приводит файл к свежему снимку БД, но не доказывает старое
желание. Постоянный валидированный отказ даёт `failed`; временная недоступность
остаётся `applying`.

## Миграция и порядок выпуска

Миграция добавляет nullable/default-поля и индексы; прежние события остаются
аудиторской историей. Порядок выпуска обязателен:

1. Выпустить миграцию, panel API и workers с optional revision и
   `VIP_LIFECYCLE_REQUIRE_REVISION=false`; старые producer-запросы продолжают
   работать, а Redis fast path уже удалён.
2. Выпустить сайт, который посылает revision, текущий HMAC timestamp,
   обрабатывает оба `409` и ожидает status вместо трактовки `202` как доставки.
3. Убедиться по журналам, что запросов без revision больше нет, включить
   `VIP_LIFECYCLE_REQUIRE_REVISION=true` и выполнить smoke точного выпуска.

Откат шага 2 не требует отката БД: флаг остаётся `false`. Откат панели на код,
не знающий новые nullable-поля, также безопасен. Существующие role, whitelist и
clan события используют ту же outbox без `correlation_id`; их публичный договор
не меняется, но публикация для них также происходит только relay после commit.

## Приёмка

- HMAC принимает границы окна ±300 секунд и отклоняет 301 секунду, неверный
  формат и неверную подпись;
- одинаковый `event_id` с тем же хешем идемпотентен, с другим телом даёт 409;
- параллельные запросы одного игрока сериализуются, unique player+revision
  оставляет одного победителя;
- перестановки `4 -> 5` и `5 -> 4` дают одинаковое итоговое состояние, а
  проигравшее событие получает `superseded`;
- роль без активного VIP-tier, роль с panel access, игрок без EOS, ручное
  назначение и активная `vip_subscriptions` отклоняются до мутации;
- lifecycle повторно получает непустой снимок серверов после preflight;
- worker не видит задачу до commit, rollback не оставляет Redis-сообщение;
- работающий сервер получает `applied` только после подтверждённого RCON и
  финальной проверки состояния; остановленный — после устойчивой записи файла;
- падения relay/worker до и после `XADD`, записи файла, RCON result,
  `applied_at` и `XACK`, а также restart/reclaim не теряют и не удваивают
  бизнес-эффект;
- боевой smoke подтверждает status без публикации платформенных ID и путей.

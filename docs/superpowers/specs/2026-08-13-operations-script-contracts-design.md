# Проверки эксплуатационных скриптов и цепочки аудита — проект решения

## Цель

Вернуть в актуальный `dev` самостоятельный защитный контур для скриптов, которые
устанавливают, развёртывают, пересобирают и удаляют панель, а также для
внеполосной проверки цепочки аудита. Переносится не старая ветка целиком, а
только заново проверенные контракты текущих файлов.

## Выбранная граница

### Эксплуатационные Bash-скрипты

Тесты запускают реальные копии текущих скриптов, но заменяют через `PATH` все
команды, способные изменить хост: `docker`, `systemctl`, `install`, `rm` и
другие. Подмены пишут точные аргументы в журнал внутри временного каталога.
Так проверяются порядок, кавычки, коды возврата и прекращение работы после
ошибки без доступа к реальным Docker, systemd и системным путям.

Проверяемые контракты:

- все скрипты имеют корректный Bash-синтаксис и строгий режим;
- `bootstrap` и `install-host-bridge` отказывают до первой мутации при
  неуспешном preflight;
- ошибка дочернего установщика возвращается вызывающему `bootstrap`;
- `deploy-tk104` требует env-файл, сохраняет аргументы Compose и не объявляет
  успех, если API не стал healthy или HTTP-проверка завершилась ошибкой;
- `rebuild` и `uninstall` ничего не меняют без точного подтверждения, а ошибка
  обязательного шага не позволяет перейти к следующим;
- `verify-bridge` обменивается настоящими length-prefixed JSON-кадрами через
  временный Unix-сокет и прекращает цепочку на первом отсутствующем ответе.

### Проверка цепочки аудита

Интеграционный тест создаёт отдельную временную БД, применяет текущие миграции,
вставляет строки через настоящий триггер `audit_log`, запускает реальный
`scripts/verify-audit-chain.ts` отдельным процессом и затем повреждает
`row_hash` или `prev_hash` только после временного отключения append-only
триггера. Проверяется точный идентификатор первой повреждённой строки и
различие кодов результата: `0` — целая цепочка, `1` — доказанное повреждение,
`2` — конфигурация или зависимость недоступна.

## Найденный текущий дефект

`scripts/deploy-tk104.sh` после исчерпания цикла ожидания не проверяет итоговый
`status`, подавляет ошибку `curl` через `|| true` и всегда печатает
`Deploy complete`. Красные тесты должны сначала воспроизвести обе ветки.
Минимальный фикс: явный отказ после таймаута API и обязательный HTTP-успех
локальной проверки через Caddy; порядок build → up → API healthy → HTTP probe →
status остаётся прежним.

## Встраивание

Корневой `pnpm test:scripts` последовательно запускает тесты эксплуатационных
скриптов, shadow-diff и цепочки аудита. CI уже применяет миграции до этого шага;
эта последовательность дополнительно закрепляется статической проверкой.
Audit-набор допускает отсутствие БД только вне CI, но при переданном
`DATABASE_URL` всегда исполняется и не может тихо пропустить тесты.

## Отвергнутые варианты

- Слить `chore/reattestation-coverage-gaps`: ветка отстаёт на сотни коммитов и
  смешивает несвязанные runtime-изменения.
- Запускать настоящие host-команды: недопустимо для локальной разработки и CI.
- Ограничиться `bash -n`: синтаксис не доказывает порядок, fail-closed и
  корректность framed-протокола.
- Мокировать сам `verify-audit-chain`: это не проверило бы миграционные триггеры
  и каноническую форму хеша.

## Риски и ограничения

- Тестовые подмены обязаны перекрывать каждую потенциальную host-мутацию; любое
  расширение скрипта должно падать на неизвестной команде, а не обращаться к
  хосту.
- Временные БД получают уникальные имена и удаляются в teardown; тест никогда
  не изменяет исходную БД.
- Проверка не заменяет ручную приёмку реального production deploy, но запрещает
  ложный программный успех его управляющего скрипта.
